# Vertex One — règles non négociables

Suite de gestion multi-tenant pour entreprises de services au Cameroun. Spécifications complètes dans `docs/` :
`cahier-des-charges-suite-locale-entreprises-services.md` (point d'entrée), `strategie-suite-locale-entreprises-services.md`, et `palier-0` à `palier-6-*-specification-technique.md`.

**Construire les paliers dans l'ordre (0 → 6), chacun testé et déployable avant le suivant. Ne jamais avancer au palier suivant tant que le test de fuite multi-tenant du palier en cours n'a pas échoué comme prévu (voir palier-0, section 9).**

## Règles de sécurité multi-tenant — sans exception

- Toute nouvelle table de données porte une colonne `entrepriseId` — sans exception — et reçoit une politique Row-Level Security dès sa création, avec `FORCE ROW LEVEL SECURITY` (sans quoi la policy ne s'applique pas au propriétaire de la table — précisément le rôle utilisé par la connexion applicative). Utiliser `pgPolicy()`/`.enableRLS()` de Drizzle dans `src/db/schema.ts` plutôt que du SQL séparé, et ajouter la clause `FORCE ROW LEVEL SECURITY` correspondante dans une migration custom (`drizzle-kit generate --custom`) — voir `drizzle/0001_force_row_level_security.sql`.
- **`DATABASE_URL` doit toujours pointer vers un rôle Postgres créé avec `NOBYPASSRLS`, jamais le rôle "owner" par défaut de Neon.** Le rôle owner (`neondb_owner` ou équivalent) a `BYPASSRLS` par défaut sur Neon : `FORCE ROW LEVEL SECURITY` ne le contraint pas, et toutes les politiques RLS deviennent silencieusement inactives — sans erreur, sans avertissement, une fuite totale entre entreprises indétectable en revue de code. Vérifié par exécution réelle du test de fuite (palier 0), qui échouait entièrement avec le rôle owner et passe avec un rôle restreint. Le rôle owner sert uniquement aux migrations, via `DATABASE_URL_MIGRATIONS` (voir `drizzle.config.ts` et `.env.example`).
- Toute requête vers une table protégée par RLS passe par le helper `avecEntreprise()` (voir `src/db/client.ts` et palier-0 section 6), qui exécute `SELECT set_config('app.entreprise_id', ..., true)` (jamais `SET LOCAL ... = $1` — syntaxe invalide côté protocole préparé Postgres, confirmé par erreur réelle) et la requête dans **la même transaction** Drizzle. Jamais de requête RLS en dehors de ce helper — avec le driver `neon-serverless` (jamais `neon-http`, qui ne supporte pas `db.transaction()`).
- Exception : les tables consultées par Better-Auth (utilisateur, session, compte) restent en RLS permissive, car ses requêtes s'exécutent avant qu'une session authentifiée n'existe. La RLS stricte s'applique aux tables métier uniquement. Cas particulier : une table qui a besoin d'une recherche anonyme par jeton secret (ex. `invitation`) peut avoir une politique de lecture permissive uniquement quand `app.entreprise_id` n'est pas positionné, jamais en écriture — voir `invitation` dans `src/db/schema.ts` pour le modèle à suivre.
- **Sur une connexion Neon fraîche (via le pooler), `current_setting('app.entreprise_id', true)` renvoie une chaîne vide `''`, pas SQL `NULL`.** Un test `OR ... IS NULL` pour détecter "aucune session active" ne se déclenche donc jamais — bug réel rencontré en testant le lien d'invitation anonyme, qui restait introuvable malgré une policy qui semblait correcte. Toujours écrire `nullif(current_setting('app.entreprise_id', true), '') IS NULL` pour ce genre de vérification.
- Aucune fonction serveur ne fait confiance à une donnée envoyée par le client (rôle, entrepriseId) — uniquement à la session signée par le serveur (Better-Auth).
- Toute action ou tout accès à une route vérifie `peut()`/`portee()` et, si la fonctionnalité est verrouillée par forfait ou add-on, `disponible()` — toujours côté serveur, jamais seulement dans l'interface.
- Après chaque nouveau module touchant à des données d'entreprise, un test délibéré doit vérifier qu'une entreprise fictive ne peut techniquement pas accéder aux données d'une autre.
- Tout identifiant transmis à un service externe partagé entre plusieurs entreprises clientes (Migadu, CinetPay, le prestataire de chat...) est préfixé par l'`entrepriseId`.

## Latence de connexion Neon — à connaître avant de crier au bug

La toute première connexion WebSocket qu'un process établit vers Neon via `drizzle-orm/neon-serverless` peut prendre 10 à 15 secondes (mesuré : 13,4s), contre ~1s pour les connexions suivantes une fois le pool "chaud". Symptômes déjà rencontrés à cause de ça : un test E2E qui échoue juste après un redémarrage du serveur de dev ou dans une nouvelle session, avec un timeout générique et aucune trace d'erreur applicative. Avant de chercher un bug dans le code : relancer une deuxième fois (le pool du process encore actif reste chaud), et prévoir un timeout de test généreux (60s minimum, voir `playwright.config.ts`) pour les parcours qui enchaînent plusieurs transactions réelles.

Au-delà du pool froid : sous sollicitation intensive prolongée (plusieurs heures de tests répétés), une requête isolée peut ponctuellement prendre 20 à 30 secondes même sur un pool déjà chaud (mesuré : 26s pour un simple `UPDATE`) — vraisemblablement le plan Neon gratuit qui régule/suspend le compute. Pour un parcours E2E qui enchaîne plusieurs Server Actions réelles (inscription, création, plusieurs transactions), donner un timeout par test bien au-delà de la somme attendue des étapes (`test.setTimeout(150_000)` par exemple) plutôt que de suspecter une régression dès qu'un test dépasse son budget habituel.

Ne pas oublier `expect: { timeout: 15_000 }` dans `playwright.config.ts` en plus du timeout global du test : une Server Action suivie d'un re-rendu prend régulièrement 5 à 8s de bout en bout, mais chaque `expect().toBeVisible()` a son **propre** timeout par défaut (5s), indépendant du timeout global du test. Symptôme observé sans ce réglage : l'action serveur réussit (confirmé dans les logs du serveur de dev), mais l'assertion abandonne quand même et coupe la requête en cours, laissant une erreur serveur trompeuse ("The destination stream closed early") qui ressemble à un vrai bug applicatif alors que ça n'en est pas un.

**Degré supplémentaire, rencontré en construisant le Palier 2** : après plusieurs heures cumulées de tests répétés dans une même session (migrations, E2E, Vitest, scripts de vérification manuels), la latence via `drizzle-orm/neon-serverless` (WebSocket) peut dépasser 60 secondes pour de simples `DELETE`/`SELECT`, au point qu'un test E2E avec `test.setTimeout(220_000)` échoue quand même sur la toute première étape (`page.fill` sur un champ de formulaire) et que le hook `afterAll` (quelques requêtes de nettoyage) dépasse lui-même son timeout de 60s — sans lien avec le code applicatif (confirmé : redémarrer le serveur de dev avec cache vidé n'a rien changé). **Fait notable** : dans ces conditions, une connexion `pg` classique (`new Client({connectionString: DATABASE_URL_MIGRATIONS})`, driver TCP direct, utilisée par les scripts de nettoyage ad hoc de ce projet) reste nettement plus réactive que le driver WebSocket `neon-serverless` — utile pour un nettoyage ou une vérification ponctuelle quand l'app elle-même semble bloquée, sans que ça indique un bug dans `avecEntreprise()`/`db.transaction()`. Dans ce cas de figure, inutile de relancer le test en boucle : le code est déjà validé par ailleurs (tests Vitest isolés + vérification visuelle manuelle) tant que le problème reste confiné à la latence, jamais à une erreur logique reproductible sur la même assertion.

**Conséquence concrète découverte en construisant le Palier 4** : quand un `afterAll` timeout ou qu'une déconnexion Neon interrompt une suite Vitest en plein milieu, son nettoyage ne s'exécute jamais — les lignes `entreprise`/`utilisateur`/etc. de ce run restent en base pour de bon. Accumulées sur plusieurs sessions, elles ont fini par faire échouer des tests par ailleurs corrects : une `entreprise`/`invitation` orpheline portant un jeton codé en dur (`"jeton-test-kiro"`) est entrée en collision avec la ligne du run suivant sur `invitation_jeton_unique` (23505) dès que la suite complète a pu enfin tourner sans interruption. Deux correctifs distincts, pas un seul : (1) toute valeur qui doit être unique dans un test (jeton, numéro) se dérive d'un id généré à l'exécution plutôt que d'être codée en dur, pour rester valide même si le nettoyage d'un run précédent n'a jamais eu lieu ; (2) un nettoyage ponctuel des résidus (`entreprise where nom like 'TEST %'`, en cascade sur toutes les tables portant `entrepriseId` puis `account`/`session` de Better-Auth qui n'en portent pas) reste sûr à faire de temps en temps via `DATABASE_URL_MIGRATIONS` — ce préfixe `"TEST "` n'est utilisé par aucune vraie entreprise cliente.

## Resend — domaine vertexone.cm vérifié (2026-09-19)

Le domaine `vertexone.cm` est vérifié sur Resend (DKIM/SPF/CNAME créés dans Cloudflare DNS, région eu-west-1) et `src/lib/email/client.ts` envoie depuis `notifications@vertexone.cm` — envoi réel confirmé vers deux adresses dont une non propriétaire du compte. Avant cette date, l'expéditeur de bac à sable `onboarding@resend.dev` n'atteignait que le propriétaire du compte (403 `validation_error` sinon). Un test automatisé qui envoie à une adresse `@*.test` reste refusé/inutile : ne pas s'en servir pour valider l'envoi réel.

`envoyerEmail()` accepte un paramètre `attachments` (`{ filename, content: Buffer }[]`), transmis tel quel au SDK Resend (`content?: string | Buffer` côté `EmailApiAttachment` — confirmé en lisant `node_modules/resend/dist/index.d.mts`, pas seulement supposé). Utilisé par `envoyerDevis`/`envoyerFacture` (`src/lib/actions/{devis,facture}.ts`) pour joindre le PDF généré à la volée (`src/lib/pdf/rendu.tsx`) — aucune conversion base64 manuelle nécessaire.

Un envoi réel (devis/facture) cumule requête Neon + rendu PDF (CPU) + appel réseau Resend : plus lent qu'une Server Action ordinaire. Dans `tests-e2e/palier-1-crm-facturation.spec.ts`, l'assertion qui suit un clic sur "Envoyer..." utilise un timeout local de 30s (au lieu des 15s globaux de `playwright.config.ts`) — passe en solo sous 15s mais dépasse 15s quand Playwright fait tourner plusieurs tests en parallèle (contention CPU/Neon), constaté réellement, pas anticipé.

## Accès aux modules choisi par l'Administrateur (2026-09-20)

L'Administrateur choisit, pour chaque Manager/Employé (à l'invitation ou ensuite dans Paramètres → Équipe), les modules auxquels la personne a accès : colonne `utilisateur.modulesAutorises` (null = tous ceux du rôle), copiée depuis `invitation.modulesPropose` à l'activation. La liste ne fait que **restreindre** la matrice du rôle, jamais l'élargir (voir `peut()`/`portee()` dans `src/lib/permissions.ts`, et `src/lib/modules-libelles.ts`).

**Toujours appeler `peut(utilisateurConnecte, ...)` / `portee(utilisateurConnecte, ...)` avec l'utilisateur connecté entier, jamais `utilisateurConnecte.role`** : passer seulement le rôle ignore silencieusement la restriction choisie par l'Administrateur, sans erreur ni avertissement. Même règle pour `itemMenuVisible()`/`libellesMenuVisibles()`. Un nouveau module doit aussi être ajouté à `LIBELLES_MODULES` (`src/lib/modules-libelles.ts`) pour apparaître dans le sélecteur.

## Pages publiques envoyées au client — devis, factures, signatures (2026-09-20)

Le client répond sans compte, depuis un lien à jeton : `/devis/[jeton]` (accepter/refuser), `/facture/[jeton]` (accepter/contester, puis payer maintenant ou plus tard), `/signature/[jeton]` (signer/refuser). Le jeton (32 caractères aléatoires) est l'unique autorisation.

- **Ne jamais ouvrir en lecture anonyme une table métier stricte** (`devis`, `facture`, `demande_signature`, `document`…). Un jeton se résout par une table dédiée à carve-out (`lien_client_document`, `signataire`) qui ne renvoie qu'un identifiant d'entreprise et de document ; toutes les données sont ensuite lues via `avecEntreprise(entrepriseId)` avec l'entrepriseId de CETTE ligne, jamais une valeur du navigateur. **Ne jamais faire de `db.select()` avec jointure entre une table à carve-out et une table stricte** : la jointure renvoie zéro ligne sans erreur (bug réel trouvé : la page `/signature/[jeton]` affichait « lien invalide » à tous les clients).
- Toute réponse du client enregistre sa date et son adresse IP côté serveur (`headers()`), et un motif éventuel ; le texte saisi par un client est échappé (`echapper()`) avant d'entrer dans un email.
- **Les emails d'alerte partent APRÈS la réponse (`after()` de `next/server`)** : le rendu du certificat PDF et les envois Resend ont pris jusqu'à 60 s, le client ne doit jamais les attendre.
- Quand le dernier signataire signe : le contrat et son certificat horodaté sont fusionnés en un PDF signé (`pdf-lib`), **rangé directement dans le dossier du client**, et envoyé à l'Administrateur, à l'auteur de la demande et au signataire (`src/lib/signature/finalisation.ts`). Si l'original n'est pas un PDF, l'original et le certificat sont envoyés séparés.
- **CinetPay exige un numéro au format international** (`+237…`) : les contacts sont saisis au format local (« 690 11 12 22 »), d'où `telephoneInternational()` (`src/lib/cinetpay/utilitaires.ts`). Sans elle, le paiement échouait avec « must be in international format » pour la plupart des clients.

## One Chat — messagerie intégrée (2026-09-20)

One Chat n'utilise **aucun prestataire externe** : les messages vivent dans notre base (`message_canal`, `lecture_canal`, RLS standard + FORCE), à la place du Stream Chat de la spec d'origine (jamais branché — `src/lib/chat/client.ts` reste une coquille inoffensive qui ne fait qu'attribuer les identifiants de canal). La conversation se met à jour par lecture régulière (3 s si l'onglet est visible, 20 s sinon) de `GET /app/messagerie/messages`, pas par WebSocket : Vercel ne tient pas de connexion longue.

- Visibilité : un canal PROJET suit la portée des Projets ; « Général » (créé à la première visite) et les canaux libres sont ouverts à toute l'entreprise. **Toute lecture ou écriture passe par `canalAccessible()`** (`src/lib/messagerie/acces.ts`) — jamais un identifiant de canal pris tel quel dans la requête.
- Un message supprimé est vidé (`contenu = ''`, `supprime_le`) mais garde sa place : le texte n'est plus jamais renvoyé au navigateur. Suppression : l'auteur ou l'Administrateur.
- La mise à jour incrémentale compare des horodatages (`mis_a_jour_le`) : **utiliser `now()` de la base (`sql\`now()\``), jamais `new Date()`**, pour ne mêler qu'une seule horloge.
- **Messages directs** : canal de type `DIRECT`, visible de ses deux seuls membres (`membre_canal`) ; identifiant déterministe (les deux identifiants triés) donc jamais deux conversations pour la même paire. Le collègue ciblé est relu en base : même entreprise, actif, jamais un client du portail ni soi-même. `canalAccessible()` exige l'appartenance pour un canal DIRECT.
- **Pièces jointes** (une par message, 4 Mo) : mêmes contrôles d'octets que One Form (`validerFichier()`), stockées dans R2 sous `entrepriseId/messagerie/…`, **jamais servies par leur seul lien** : `GET /app/messagerie/fichier/[messageId]` revérifie l'accès au canal (image en ligne, le reste en URL signée à téléchargement forcé). Supprimer un message efface aussi le fichier dans R2.
- **Notifications** : badge de non-lus dans le menu et dans le titre de l'onglet (lecture toutes les 30 s), notifications du navigateur quand l'onglet est masqué, et **email différé** pour un message direct resté non lu 3 minutes (un email par conversation, jamais deux fois : `notifie_le`). Le worker (`verifier-messages-a-notifier`, toutes les 3 min, voir `crontab`) ne traite que les entreprises marquées à l'envoi d'un message direct (`entreprise.messages_a_notifier_depuis`), jamais un balayage complet. Pas de push mobile application fermée (exigerait des clés VAPID et un service worker).
- **Présence** : `utilisateur.derniere_activite_le`, mis à jour (au plus toutes les 30 s) par les lectures de la messagerie ; « en ligne » = moins de 2 minutes, calculé avec `now()` de la base.
- **Groupes privés** : canal de type `PRIVE` (membres dans `membre_canal`, créateur dans `canal.cree_par_id` qui seul gère les membres ; un membre peut quitter, pas le créateur). **Privé signifie privé pour tous, Administrateur compris** : `canalAccessible()` exige l'appartenance pour DIRECT et PRIVE, sans exception de rôle. Ne jamais contourner cette fonction (lecture de messages, fichiers, recherche, mentions).
- **Réactions** : liste fermée d'emojis (`EMOJIS_REACTION`, validée côté serveur), une par personne et par emoji (index unique). Réagir fait « bouger » le message (`mis_a_jour_le = now()`) pour que la lecture incrémentale le redistribue.
- **Fils de discussion** : une réponse est un message avec `parent_id` (un seul niveau), absent de la chronologie ; répondre ou supprimer une réponse fait bouger le message d'origine. `chargerMessages({ fil })` reste borné au canal demandé (un identifiant de fil d'un autre canal ne renvoie rien).
- **Mentions** `@Nom Complet` : décidées côté serveur (`extraireMentions`, `src/lib/messagerie/mentions.ts`), longest-match d'abord, jamais une adresse email ; seules les personnes qui peuvent VRAIMENT voir le canal sont retenues (`canalAccessible` sur la personne mentionnée). Email différé si non lu à 3 min (`mention_message.notifie_le`). Pas de mention dans un message direct (l'email « vous a écrit » couvre déjà).
- **Recherche** : `ILIKE` sur le texte et le nom des pièces jointes, **uniquement** dans les canaux de `canauxAccessibles()` ; les jokers `% _ \\` saisis sont neutralisés (`echapperMotifRecherche`). Un résultat ouvre le canal centré sur le message (`chargerAutour`).
- **Lecture adaptative** : 3 s tant que ça bouge, jusqu'à 10 s en conversation calme, 20 s onglet masqué (`delaiProchaineLecture`). Chaque lecture coûte plusieurs requêtes : ne pas la resserrer sans mesurer.
- Pas encore : messages épinglés, modification d'un message envoyé, réactions personnalisées, appels audio/vidéo.

## Règles métier — sans exception

- Une facture n'est jamais supprimée, quel que soit le rôle — seule une annulation (`AvoirFacture`) est possible.
- Un numéro de facture n'est généré qu'au moment exact de l'émission, jamais avant, via une opération atomique protégée contre les créations simultanées.
- Un document classé `PIECE_IDENTITE` ou `DONNEES_SANTE` reste restreint au responsable du dossier et à l'Administrateur, quel que soit l'accès normal au dossier qui le contient ; sa consultation est journalisée ; sa suppression réelle doit être possible sur demande légitime.
- Le salaire d'un employé n'est jamais rempli automatiquement et reste visible uniquement par l'Administrateur et l'intéressé.
- Aucun calcul de cotisation sociale (CNPS), d'IRPP, ou de bulletin de paie n'est implémenté dans le produit — seule l'exportation des données vers un partenaire est prévue.
- Le discours commercial et le code ne doivent jamais présenter le paiement Mobile Money (CinetPay) comme "instantané" ou "direct" — le modèle est custodial, avec un délai de reversement de 8 jours par défaut (réductible sur demande après KYC), voir stratégie, section 3.

## Indépendance des modules — chaque module doit rester vendable et utilisable seul

Chaque module de Vertex One (CRM, Facturation/Books, Achats, RH, Marketing...) doit pouvoir être utilisé indépendamment des autres, même si des données sont naturellement partagées entre eux (ex. un Contact existe pour le CRM comme pour la Facturation). Un module ne doit jamais imposer, en dur dans le schéma, le passage préalable par un autre module.

**Défaut réel trouvé et corrigé (2026-09-07)** : les 6 tables de documents Ventes (`devis`, `facture`, `bonCommandeVente`, `factureRecurrente`, `recuVente`, `factureAcompte`) avaient un `dealId` **obligatoire** (FK vers `deal`, une entité 100% CRM — pipeline, statut, probabilité). Conséquence : impossible techniquement de créer une facture sans être passé par le pipeline CRM au préalable, alors qu'une facture ne devrait dépendre que d'un Client, jamais d'une opportunité commerciale. Corrigé en ajoutant `contactId`/`compteId`/`assigneAId` directement sur ces 6 tables (`contactId` obligatoire, `compteId` dénormalisé optionnel comme `deal.compteId`, `assigneAId` obligatoire) ; `dealId` devient optionnel, renseigné seulement quand le document provient réellement du CRM. Voir `src/lib/facturation/client-document.ts` (`resoudreClientVente()`/`memeClientVente()`), point d'entrée standalone sur `src/app/app/contacts/[id]/page.tsx`.

**Comment appliquer cette règle à un futur module** : avant d'ajouter une colonne `NOT NULL` référençant une table d'un *autre* module, se demander si ce module cible pourrait raisonnablement être vendu/désactivé indépendamment. Si oui, la référence doit être nullable, et le module doit porter directement les colonnes dont il a besoin pour fonctionner seul (client, propriétaire/`assigneAId` pour la portée) — jamais les dériver uniquement via une jointure vers l'autre module. La portée (`idsVisibles()`, `src/lib/portee.ts`) doit toujours filtrer directement sur une colonne `assigneAId` propre à la table du module courant, jamais via un détour par une table d'un autre module (le module Achats, `depense`/`bonCommandeAchat`/`factureFournisseur`, a toujours fait ça correctement — c'est le patron de référence).

Migration d'une contrainte `NOT NULL` existante en situation similaire : patron **expand → backfill → migrate → contract** en plusieurs migrations séparées (ajouter les colonnes nullable → backfiller les lignes existantes → aligner tout le code applicatif → seulement alors resserrer en `NOT NULL`), jamais en une seule migration atomique — chaque étape intermédiaire doit laisser `tsc`/la suite de tests vert.

## File d'attente (graphile-worker)

- **Le worker (`npm run worker`, `src/worker/run.ts`) doit se connecter via `DATABASE_URL_WORKER` (endpoint direct Neon, sans "-pooler"), jamais `DATABASE_URL`/`DATABASE_URL_MIGRATIONS`.** Le pooler Neon (PgBouncer, mode transaction) recycle les connexions entre requêtes et casse LISTEN/NOTIFY, sur lequel graphile-worker s'appuie pour une connexion persistante — symptôme rencontré : "Connection terminated unexpectedly" en boucle, worker qui redémarre sans jamais traiter de job. Voir `.env.local` pour la variable, et `src/worker/run.ts` pour le commentaire complet.
- Dans `src/worker/run.ts` (et tout script autonome équivalent), charger `dotenv` puis importer le reste **dynamiquement** (`await import(...)`) à l'intérieur de `main()`, jamais par des `import` statiques en haut de fichier : un import statique est hissé par ESM et s'évalue avant `config()`, donc avant que les variables d'environnement n'existent — `src/db/client.ts` construirait son `Pool` avec une chaîne de connexion vide, sans erreur visible au démarrage (l'échec n'apparaît que quand une tâche essaie réellement une requête).
- Les tâches elles-mêmes (`src/worker/tasks/*.ts`) utilisent `avecEntreprise()` (rôle applicatif restreint, RLS active) pour toute donnée métier — le rôle élevé du worker ne sert qu'à sa propre file d'attente (schéma `graphile_worker`, hors RLS car aucune donnée multi-tenant).
- **Chaque `npm run worker` lancé en arrière-plan doit être explicitement arrêté (`taskkill /PID ... /F` sur Windows, pas seulement l'arrêt de la tâche shell qui l'a lancé) avant d'en relancer un autre.** Rencontré en pratique : trois instances du worker sont restées actives simultanément après plusieurs redémarrages, chacune maintenant sa propre connexion persistante à Neon, ce qui a dégradé les performances de tout le reste (serveur de dev, tests E2E) jusqu'à leur terminaison. Vérifier avec `tasklist | grep node.exe` (ou `wmic process ... get CommandLine` pour identifier lequel est lequel) avant de conclure à un bug ailleurs.

## Tests Playwright et `getByText` — toujours `{ exact: true }` près de la sidebar

Le pied de la sidebar (`src/app/app/menu-utilisateur.tsx`) affiche le nom complet de l'utilisateur connecté à côté du libellé de rôle (ex. "ADMIN"). `page.locator("nav").getByText("ADMIN")` sans `{ exact: true }` fait une correspondance insensible à la casse et sur sous-chaîne : si le nom de test utilisé est "Admin E2E" (ou contient "employe", etc.), le locator résout à **deux** éléments ("ADMIN" le libellé de rôle, et "Admin E2E" le nom) et Playwright lève une "strict mode violation" — un échec immédiat, pas un timeout. Trouvé en ajoutant ce pied de sidebar (nom + email + déconnexion) à la refonte visuelle : `tests-e2e/palier-0-inscription-connexion.spec.ts` utilisait justement "Admin E2E" comme nom de test. Symptôme trompeur observé en plus : le test suivant du même fichier échouait aussi avec une erreur d'authentification ("User not found") sans lien apparent — en réalité un effet de bord de l'échec du premier test (le module de test se réévalue avec un nouvel email généré, donc le second test tente de se connecter avec des identifiants qui n'ont jamais été créés). Toujours écrire `getByText("ADMIN", { exact: true })` (ou équivalent) pour tout texte de rôle/statut court susceptible d'apparaître aussi en sous-chaîne d'un nom ou email affiché ailleurs dans la même page.

## Stack

## Charte graphique et logo — à respecter dans toute nouvelle interface

Charte officielle (logo fourni le 2026-09-20) : **bleu marine `#233C7E` et orange `#ED7623`**, définis une seule fois dans `src/app/globals.css` (`--marque-bleu`, `--marque-orange`) ; toutes les nuances en dérivent. ## Next.js 16 — ce projet n'est pas la version que tu connais par défaut

Ce projet utilise Next.js 16, dont plusieurs conventions cassent avec les versions antérieures. Avant d'écrire du code touchant au routage ou au cache, vérifier `node_modules/next/dist/docs/`. Points déjà rencontrés :

- Le fichier `middleware.ts` est déprécié — utiliser `proxy.ts` avec un export nommé `proxy` (pas `middleware`). C'est le fichier où la session Better-Auth sera vérifiée pour protéger les routes.
- `cookies()`, `headers()`, `draftMode()`, ainsi que `params`/`searchParams` sont **toujours asynchrones** — plus de fallback synchrone.
- ESLint utilise le format Flat Config (`eslint.config.mjs`) ; `next lint` n'existe plus, utiliser `eslint` directement.
- Turbopack est actif par défaut sur `next dev` et `next build`.
